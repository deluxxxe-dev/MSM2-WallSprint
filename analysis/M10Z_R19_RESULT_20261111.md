# M10z-r19 owner result and analysis (2026-11-11)

Build: branch `codex/v01c20-edi-value-provenance`, source commit 9cf4b3f (M10z-r19), verified tree in `docs/CLOUD_VERIFIED.txt`.
Evidence inspected (all of it): log `MSM2-WS-v0.1c48-20261111-171411.log` (8345 lines) and three owner videos, each sampled
over its full duration: "Do not land from WS" (12.6 s), "The wall jump is misaligned with the input direction" (9.2 s),
"WebZip is misaligned with the input direction" (10.9 s). Raw log and videos are not committed.

Owner report: problems basically unchanged; in addition (also in the previous build) the hero cannot walk toward the
ground while standing on the face.

## 1. Face jump / web zip direction is rotated ~90 degrees (VERIFIED-RUNTIME + video)
- Video pose during the jumps: camera fixed behind/above the hero looking DOWN the face (street at the top of the
  screen). So screen-up = down the building (world -y), screen-right = one of the horizontal face axes
  +-(0.35, 0, 0.94) (wall normal n = (0.937, 0, -0.349)).
- Log `WS_FACE_JUMP_INPUT` in that pose (08:16:23-08:16:35): `screen_fwd=0.34,-0.16,0.92` (the horizontal face axis),
  `screen_right=0.06,0.99,0.15` (world up). Both are 90 degrees off the video.
- Resulting directions: stick up (-0.09, 1.00) -> dir (0.34, -0.25, 0.91) = sideways; stick down -> opposite sideways;
  stick left (-1.00, -0.26) -> (-0.15, -0.94, -0.40) = down the building = screen up; stick right -> (0.03, 1.00, 0.07)
  = up the building = screen down. This is exactly the owner's "up/down go sideways, left goes up, right goes down".
- Cause (VERIFIED-STATIC): `faceScreenAxes()` in `source/src/NativeHooks/camera_ref.cpp` reuses the WallRun stick-drive
  formula (actor_writer M5c-r8: f = manager+0xD34, u = +0x10, c = f x u, screen forward = proj(c) x n). That formula was
  proven only for the camera during WallRun. In the face-as-ground state the measured c is the camera look axis itself
  (c ~ +-y in the pose above), so proj(c) x n is 90 degrees off. Which matrix row is which in this state is NOT proven
  (comment at actor_writer.cpp:269 says +0xD24 right, +0xD34 up, +0xD44 forward, +0xD54 position; M5c uses +0xD34 as
  forward) -> do not rely on row semantics.
- After a web zip the game camera swings (video 3); `screen_fwd` then changes per jump (e.g. (0.14,-0.92,0.37),
  (-0.34,-0.27,-0.90), (0,-1,0)), so zip directions differ from jump to jump.

## 2. Cannot walk toward the ground on the face (VERIFIED-RUNTIME)
- `WS_FACE_MOVE_SAMPLE` (200 samples while pinned with the stick pushed): 10 game steps had a downward wall-up component
  and all 10 were undone by our store (`store_dy` > 0); 1 upward step passed.
- Cause (VERIFIED-STATIC): M10z-r18 drop limits. Transform::SetPosition is called 3-4 times per frame for the hero; the
  same-frame branch (`dt < 0.002`) sets `mvB[1] = mvA[1]` for any downward change > 2 mm, and the first call of a frame
  allows only 6 m/s * dt. A walking step written in a later call of the frame is therefore always removed.

## 3. Stopping from WS does not land on the face (cause UNKNOWN)
- Video 1: after the stop the hero stays in the fall pose close to the wall for the whole clip; the camera stays in a
  rolled pose; no standing pose.
- Log: `STOP_PUSH start_d=0.20`, `WALL_LANDED t=0.31 plane=wall_point_0x338`; the hold then has
  `pin_drops_undone=865`, `dy_game_sum=-52.6 m` in 22 s: the game keeps its airborne (falling) state and our stores
  cancel the fall every frame. A web zip (owner) switches the game state and the hero then stands.
- In M10z-r6 (commit ac8259b, thread stores only) the same push did produce standing ("stands upright without a jump").
  Changes since then that touch this path: SetPosition hook path (r15), per-call processing (r16), strict drop undo and
  plane handling in every SetPosition call (r17/r18). HYPOTHESIS A: overriding every SetPosition call keeps the hero
  5 cm off the wall point / removes the game's own snap or downward probe step, so its ground test along -n never
  succeeds. HYPOTHESIS B: the game needs a real collision contact while moving toward the face (sweep), which the
  position pin prevents.

## 4. Web zip visual
- The web line goes toward the hero's feet (owner). The zip animation and web target are the game's (A is passed
  through); only our 18 m/s impulse was added. Not analysed further; depends on item 1.

## Facts to keep (from earlier runs, still valid)
- Face-as-ground state exists: with the hero gravity block (SetGravityVector hero block) held at up = n and no external
  position stores, the game stands, walks and jumps on the face smoothly (owner irregular run, M10z-r11/r12).
- During a face jump the game writes zero position steps (M10z-r17b `WS_FACE_JUMP_STEP`), so the jump motion must be ours.
- External stores must only happen when a correction is needed (store races caused the walking snag).
